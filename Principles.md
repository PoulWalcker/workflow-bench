# Principles

Инженерные правила Workflow Bench. Продуктовые требования находятся в
[SPEC.md](SPEC.md), расположение компонентов — в [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. rTernarity: три ответственности, не культ трёх файлов

Верхний уровень: **Definition → Experiment → Evaluation**. Декомпозируем
ответственность дальше только тогда, когда в ней появились самостоятельные
обязанности. Каждая часть имеет понятные вход, работу и результат.

Не создаём пустые ветки, обёртки и классы для достижения числа три. Коллекции
задач, сценариев и тестов могут содержать любое число элементов. Функциональный
смысл важнее симметрии дерева. Это соответствует формулировке rTernarity в
[CONTRIBUTING.md AutoWFBench](https://github.com/aleski-green/AutoWFBench/blob/main/CONTRIBUTING.md).

Точка входа и общие контракты не становятся дополнительными продуктами.
Архитектурную границу объясняем обязанностью, а не названием папки.

## 2. Один владелец каждого поведения

Одна реализация состояния Telegram; два способа доступа к нему — API и UI.
Один native n8n формат без DSL/compiler, один путь исполнения, один расчёт score.
Harbor владеет жизненным циклом sandbox, мы — правилами исследовательского эксперимента.

Task содержит человеческую постановку, входной контракт/учебный пример, кейсы,
предметные проверки, рубрику и контроль. Новая Task на прежних возможностях меняет
только свой каталог. Симулятор, runtime и Judge переиспользуются; бизнес-правила
не прячутся в общем prompt, binder или evaluator. Параметры, наблюдения через tools
и приватные ожидания остаются разными входами, а не одним case для кандидата.

Интеграция внешнего Composer живёт отдельно от общего ядра и использует штатную
границу Harbor agent. Точка сборки выбирает её из конфигурации; Experiment не
ветвится по имени harness. Адаптер не реализует внутреннее планирование агента.

Не вводим plugin registry, универсальный backend, фабрику фабрик или базовый
класс для единственной реализации. Общий helper выделяем при реальном повторении
смысла, а не просто похожем синтаксисе. Две понятные строки лучше лишнего слоя.

## 3. Конфигурация вместо машинного хардкода

Пути пользователя, адреса, порты, имена моделей, credentials, каталоги результатов
и бюджеты задаются через CLI, env или конфигурацию — один источник на параметр.
Предлагаемый приоритет: явно заданная CLI-опция, затем env, затем документированный
безопасный default. Точную карту параметров закрепляет реализация, не несколько
параллельных конфигов.

Никаких `/Users/<name>/...`, обязательного абсолютного пути к Codex, скрытой
зависимости от текущей директории или предположения, что свободен фиксированный
порт. Host-пути собираем через `pathlib`; сетевые имена внутри контейнеров задаём
их конфигурацией. `localhost` в контейнере не используем как неявный адрес хоста.

**Не вся константа — плохой хардкод.** Пути протокола Harbor, имена JSON-полей,
версии схем, фиксированные тестовые данные и осмысленные лимиты допустимы.
Их значение должно иметь одного владельца. Не делаем настройкой каждую строку.
Версии окружения фиксируем ради воспроизводимости, а не подстраиваем автоматически.

## 4. Читаемый код

Python, явные имена, небольшие функции с одной обязанностью. Типизируем публичные
границы и структуры обмена. Внешние JSON и аргументы валидируем на входе;
внутренний код не обрастает повторной проверкой уже гарантированных условий.

Ruff отвечает за единое форматирование и согласованный небольшой набор lint-правил.
Не добавляем второй formatter и новый type checker без конкретной потребности.
Конфигурация живёт в `pyproject.toml`; предложение для WB-02 находится
в [тикете](docs/implementation/WB-02-bootstrap.md). Не начинаем с `ALL`.
Сначала исправляем нарушение. Обоснованное исключение задаём через реальные
`lint.ignore` / `lint.per-file-ignores` с комментарием о причине в TOML и
минимальной областью. Из-за одного места глобально правило не выключаем;
целиком `src`/`tests` не исключаем. `per-file-ignores` затрагивает весь файл,
поэтому не маскирует потребность в точечной правке. `# noqa` не является штатным
выходом. Исключений заранее нет; расширение подавления требует явного объяснения.
Комментарии объясняют причину или ограничение. Длинные рассуждения и инструкции
по эксплуатации относятся к документации, а не к каждой функции.

Исключения ловим там, где можем восстановиться либо честно классифицировать ошибку.
`except Exception` допустим на границе процесса, сервера или cleanup, но не для
подавления дефектов и превращения неизвестного результата в успех.

## 5. TDD по поведению

Используем **pytest**. До coding согласуем test seams с пользователем: Interface,
наблюдаемое поведение, что проверка обнаруживает и чего не доказывает.
Предложения для первого среза находятся в WB-02–WB-05; наличие таблицы ещё
не означает согласование. В design-сессии тестовые файлы не создаём.

Для нового бизнес-правила или регрессии сначала пишем один небольшой тест,
который показывает нужное поведение и падает по ожидаемой причине. Затем
минимальная реализация, при необходимости локальный рефакторинг на green,
затем следующий сценарий. Не пишем всю будущую suite на воображаемый API.
Ожидания берём из требований и независимо разобранных примеров, не вычисляем
той же функцией/алгоритмом, который проверяем. Для Docker-конфигурации и исследовательского spike
допустимо начать с минимального воспроизводимого эксперимента; подтверждённое
поведение затем закрепляем проверкой.

| Риск | Уместная проверка |
|---|---|
| Неверный получатель или дубликат | Итоговое состояние и журнал действий симулятора |
| Расхождение API и UI | Запись одним способом, чтение другим из общего состояния |
| Невалидный native workflow или ошибка импорта/исполнения | Проверка контракта плюс реальный импорт/запуск n8n |
| Утечка скрытых данных | Интеграционная попытка чтения из недоверенного окружения |
| Неправильный stop/feedback | Малый детерминированный эксперимент с управляемыми ответами |
| Ошибка Judge | Контракт ответа, ссылки на evidence, отказ на неполном результате |

Не тестируем приватные helper-функции только ради coverage. Не фиксируем число
файлов, точную разбивку на функции, случайные ID, полный большой UI snapshot или
идеальное время исполнения. Не создаём тест на каждый getter и import.

Моки полезны для ошибок внешнего процесса, таймаутов и ответов модели. Они не
доказывают работу Harbor, n8n, sandbox или реального Judge. Минимальный реальный
сквозной контроль обязателен. Оркестрационные тесты должны проверять поведение,
а не дословный порядок всех внутренних вызовов.

Frozen evidence — публичный Interface независимой benchmark-проверки.
Проверять состояние и журнал через него необходимо: это не обход Interface
и не чтение приватных helpers кандидата. Локально выполняем настоящие loader,
validator/binder и evaluator; подменяем только внешний process/transport, время
или источник сбоя. Изоляцию, n8n и остановку доказываем реальным исполнением.

**Отбор тестов — исполняемый gate, не только marker.** Быстрые тесты находятся
в `tests/fast`, реальные контроли — `tests/integration`, будущие модельные —
`tests/model`. Каталоги появляются с поведением, не пустыми в bootstrap.
Default `pytest` запускает только fast, без сети/Docker/credentials.
В `conftest.py` WB-02 регистрирует явные `--run-integration` и `--run-model`;
`pytest_ignore_collect` не собирает соответствующие каталоги без opt-in.
Дополнительно `pytest_collection_modifyitems` отклоняет явно переданный gated
путь/помеченный item без нужного флага (включая обход testpaths или `-m`).
Классификация по пути обязательна, marker уточняет её, но не может ослабить gate.
Эти hooks только читают конфигурацию/пути, ничего не запускают.

Ресурсы создаются исключительно внутри fixtures после повторной проверки gate,
не при import/collection, не в значениях параметризации и не в root autouse setup.
Прямой запрос ресурса из fast-теста также отклоняется до побочного действия.
Integration opt-in не разрешает model tests. В WB-02–WB-05 `--run-model`
отклоняется как ещё не реализованный режим; позднее потребует явного разрешения
и файла конечных лимитов до доступа к credentials. Один флаг не заменяет разрешение.

Будущие формы запуска: `pytest` и `pytest tests/integration --run-integration`.
Это договор о конфигурации, не работающие команды текущего checkout.
Если integration запрошена, отсутствие Docker/image — ошибка preflight,
а не зелёный skip. `--collect-only` всегда без побочных действий.
Gate проверяют безопасным probe collection/setup, который не запускает контейнеры
или модель. Если нет бизнес-тестов, exit code 5 pytest честно указывается;
его не превращают в успешный suite и не добавляют `assert True`.
[pytest hooks](https://docs.pytest.org/en/stable/reference/reference.html#hooks).
Количество тестов и процент coverage не являются целью проекта.

## 6. Честная оценка

Факты берём из доверенного состояния симулятора и записей инструментов.
Текст кандидата — результат для оценки, а не доказательство исполнения.
Приватные тесты недоступны Composer и workflow. Итоговый holdout не используется
для исправлений. Схему раскрытия feedback и рубрику фиксируем до оцениваемого запуска.
Рубрику редактируют в Task (`tests/rubric.json`); manifest хранит применённый снимок.
Приватные проверки реализуют публичные требования, не вводят новые скрытые правила.

Нет данных — не значит ноль. Ошибка среды — не значит провал модели.
Полезное частичное выполнение — не значит выполненная задача. Не приписываем
нулевой расход отсутствующей статистике токенов.

## 7. Простота эксплуатации

Одна команда делает то, что написано в её описании. Быстрая проверка не начинает
оплачиваемый эксперимент. Каждая долгая операция сообщает фазу, путь к логу и
завершение; достаточно одной строки прогресса, не системы наблюдаемости.

Experiment не повторяет автоматически неизвестный вызов Composer; адаптер не
добавляет скрытый repair loop. Workflow не повторяет запись вслепую. Внутренние
повторы harness/CLI/SDK фиксируем с доступными метриками и пределами наблюдаемости,
не переписывая стороннего агента ради полного контроля провайдера. Ограничения
доступа, конечные бюджеты и подтверждение остановки обязательны.

У каждой операции есть конечный timeout. Каждый эксперимент работает в собственном
каталоге и очищает только собственные ресурсы. Не добавляем общий ledger, глобальный
scheduler, фоновые демоны или «самовосстановление» сверх согласованных попыток.

Сохраняем необходимые исходные факты один раз; отчёт ссылается на них. Не дублируем
дерево Harbor-артефактов под вторым набором названий. Не хешируем всю документацию
так, чтобы исправление README блокировало тестовый запуск.

### Минимальное логирование

Стандартный `logging`; один вызов настройки в точке входа приложения, при
появлении реального CLI в WB-04. Модули получают `logging.getLogger(__name__)`,
не добавляют handlers при импорте. `LoggerAdapter`/`extra` передают run_id,
attempt_id, case_id/replay_id и phase; ещё не назначенные ID явно отсутствуют.
Собственные Python-процессы симулятора/verifier настраивают logging в своих
entry points. Дополнительная библиотека и LoggingManager не нужны.

INFO: начало/конец setup, submission, replay, freeze, verification, cleanup,
длительность по monotonic clock, статус и ссылка на лог внешнего процесса.
Для долгой операции — короткое INFO о текущей фазе примерно раз в 30 секунд,
без ложного процента готовности. WARNING: неполные метрики, неизвестный эффект,
неполная очистка. ERROR: отказ запуска/проверки и код причины; DEBUG:
безопасные технические детали для расследования. Известный fail критерия —
результат benchmark, не обязательно ERROR инфраструктуры.

Диагностика идёт в stderr; machine-readable stdout содержит только результат
команды. При сбое сохраняем причину и путь к исходным Harbor/n8n logs, не
ретранслируем их целиком и не строим второе дерево логов. Не записываем в обычную
диагностику/feedback credentials, capabilities, полные prompts, приватные
input/state/expected и сырые исключения с ними. Формат ошибок содержит безопасные
коды и relative refs. Приватные исходные логи остаются в закрытом run-каталоге.
Логи не заменяют защищённый журнал effects, Evaluation или подтверждение stop.
Добавляем события вместе с долгой операцией, не пустую подсистему в WB-02.

## 8. Документация и завершение

Один факт — один документ-владелец, в остальных местах ссылка. README описывает
только существующие команды; roadmap отмечает только проверенный прогресс.
Новая существенная возможность сначала меняет SPEC и scope задачи.

Перед merge должно быть понятно: зачем изменение, какое поведение доказано,
какая внешняя проверка не выполнялась. Не включаем «на будущее» неподтверждённые
зависимости, дополнительные языки workflow и резервные runtime-пути.
