# WB-01 — Организация структуры проекта и компонентов

**Зависимость:** WB-00. **Актуальный статус:** [ROADMAP.md](../../ROADMAP.md).
Это задача разработки репозитория, не benchmark-задание для оцениваемой модели.

## Проблема

В старом проекте было трудно понять, какой компонент владеет каким поведением.
Новый код не должен начинаться с несвязанных папок, отдельных флоу для разных
задач и повторного создания одинаковых адаптеров.

## Цель

Создать минимальную структуру с понятными владельцами, чтобы Telegram, Composer,
runtime и Evaluation добавлялись последовательно без нового редизайна.
Структура служит рабочему коду; сама по себе большая заготовка директорий не результат.

## Прочитать

[AGENTS.md](../../AGENTS.md), [Principles.md](../../Principles.md),
[ARCHITECTURE.md](../../ARCHITECTURE.md) и разделы 2–3, 6–9
[SPEC.md](../../SPEC.md). Не исследовать старый репозиторий целиком и не переносить
его схемы как условие старта.

## Сделать

**1. Разместить существующее.** Сохранить `src/workflow_bench` как единственный
Python-пакет; оставить работающие entrypoint/help и packaging из WB-00. Создавать
`definition/`, `experiment/`, `evaluation/` только с реальными обязанностями и кодом.
Не создавать mock-services, абстрактные backend и десятки пустых файлов.

**2. Закрепить владельцев.** Общее Telegram-состояние и API/UI относятся к Definition.
Composer, compiler, адаптация Harbor/n8n и последовательность попыток — к Experiment.
Проверка evidence, Judge и scoring — к Evaluation. `contracts.py` содержит только
нейтральные используемые контракты. CLI собирает flow, но не вычисляет правильный
ответ benchmark-задачи.

**3. Разделить содержимое репозитория.** Корневой `tests/` тестирует software;
`tasks/<name>/tests/` проверяет сданный workflow. `tasks/` хранит canonical Harbor
Task, не тикеты разработки. `docs/implementation/` хранит этот тикет. `runs/`
содержит локальные результаты и не коммитится. `infra/` предоставляет общие
build-определения; task directories не копируют исходники зависимостей.

**4. Записать границы.** Обновить ARCHITECTURE по фактическому состоянию. Явно
отделить будущую карту от уже реализованного дерева. Указать запрещённые обратные
импорты и запрет выполнения кандидата в verifier с приватными тестами.
Физическая container topology проверяется в WB-02, а не считается готовой здесь.

## Критерии приёмки

- [ ] Установка пакета и help/version из WB-00 работают после структурных изменений.
- [ ] Однозначно указаны владельцы состояния Telegram, compiler, runtime, scoring
      и task-specific ожиданий; нет двух конкурирующих реализаций.
- [ ] Существующие зависимости не образуют цикл между тремя ответственностями.
- [ ] `tasks/`, software tests, implementation tickets и runtime artifacts не смешаны.
- [ ] Будущие папки не созданы только для совпадения с нарисованным деревом.
- [ ] README/ARCHITECTURE описывают реальность и отдельно план; результаты не
      выдаются за готовую изоляцию или работающий benchmark.

## Уместные проверки

Повторить installation/CLI smoke и релевантные локальные проверки. Если уже есть
реальные импорты между подсистемами, проверить разрешённые направления одним
небольшим тестом или понятным статическим правилом. Не создавать функции и импорты
специально ради такого теста. Документацию проверить на рабочие относительные ссылки.

Тест на «ровно три папки» запрещён. Здесь не требуется модельный вызов, запуск
Telegram, интеграция Judge или работающий Docker-сценарий.

## Не входит

Task registry, универсальный adapter layer, provider factory, новый язык workflow,
генерация всех четырёх Task, копирование AutoWFBench, создание Static App Model,
перенос исторических evidence, платные запуски и самостоятельный orchestrator.

## Результат для ревью

Показать фактическое дерево изменённых файлов, краткую карту владельцев,
запущенные проверки и оставшиеся границы WB-02. Не добавлять отдельный длинный
архитектурный отчёт с копией ARCHITECTURE. Источник статуса задачи — ROADMAP.
