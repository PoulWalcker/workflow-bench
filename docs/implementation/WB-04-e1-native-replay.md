# WB-04 — E1: первый реальный сквозной T1 без модели

Статус: **DONE** · 12 октября 2026 года. Этап 1 [ROADMAP](../../ROADMAP.md).

## Цель и наблюдаемый результат

Ручной `workflow.json` проходит файловую сдачу, настоящий импорт/execute n8n
в отдельном окружении Harbor и независимую проверку защищённых фактов.
На новом input возникает ровно одна отправка правильного текста в нужный чат;
остальные данные сохранены. Это первый работающий сквозной результат, но E1
завершится только после [WB-05](WB-05-e1-trust-and-failures.md).

## Основание

- [SPEC §3–6](../../SPEC.md): T1 с готовым chat_id, исполняемая симуляция,
  параметризованный native workflow; §8–11: независимые факты, ошибки и доверие.
- [ARCHITECTURE §3–5](../../ARCHITECTURE.md): native-профиль, сдача, replay,
  external JS runner, separate verifier и защищённые факты; E1 — в ROADMAP.
- [Engineering rules](../../AGENTS.md): один путь исполнения, реальные контроли,
  отсутствие бизнес-решений в binder и честная классификация результатов.

## Зависимости

[WB-03](WB-03-component-boundaries.md) завершён. Нужен доступный Docker host,
способный обеспечить требуемую изоляцию. Совместимые версии Harbor/n8n/runner
выбираются и закрепляются этой задачей; их наличие не следует из архитектурных
примеров. Автор Task с владельцем фиксирует необходимую публичную семантику
T1 API до подготовки контролей. Численная методика может оставаться неутверждённой.

## Что входит

1. Проверить доступность среды и закрепить версии/образы для реального контроля.
   Перед запуском задать конечные технические timeouts и tool/resource limits
   как настройки E1, не как одобренные бюджеты будущих измерений. Образы готовить
   до измеряемой фазы; записать версии и фактически выполненные команды.
2. Создать минимальную native T1: публичное намерение и input contract,
   синтетический учебный пример, новые технические кейсы, предметные checks и
   ручной контроль. Готовый ID не требует решателя идентичности. Профиль явно
   описывает чтение/отправку, not_found без эффекта, наблюдение эффекта и
   наличие/отсутствие idempotency. Значения из ARCHITECTURE уже публичны и не
   объявляются настоящим holdout.
3. Реализовать минимальное состояние Telegram и нужные T1 HTTP-tools: реальная
   запись, структурированные ошибки, журнал принятия/эффекта/доставки ответа.
   Host владеет reset/freeze/export/revoke; отдельная capability ограничивает
   run/case/actor, профиль, срок и число действий. Tool endpoint не раскрывает
   приватные ожидания или control-функции.
4. Пройти штатную файловую сдачу ручного native-контроля: `solve.sh` только
   предоставляет файл, не отправляет сообщения и не пишет reward. Зафиксировать
   байты после прекращения записи; проверить размер/тип/JSON и hash. Использовать
   тот же путь приёма, который затем получит кандидат, без model adapter.
5. Реализовать validator и binder принятого native-профиля: проверка node
   types/versions/options, связей и слотов; только параметры и технические
   bindings в BenchInput, результат через BenchResult. Ограничения artifact contract действуют
   и для пока неиспользуемых опций; поддержка профиля не означает доказательство
   всей семантики T2–T4. Исходная бизнес-логика неизменна, замены и hashes записаны.
6. Импортировать и исполнить файл единственным n8n CLI-путём в свежей локальной
   БД отдельного replay sandbox. Включить небольшой реальный JS Code node,
   чтобы проверить совместимость external runner с выбранным CLI, а не лишь
   соседство контейнеров. Runner также изолирован. Автоматические retries записи
   отключены; candidate packages не устанавливаются.
7. Закрыть приём действий, завершить принятые операции либо отметить unknown,
   остановить runtime, получить frozen bundle непосредственно от симулятора.
   Связать run/attempt/version/case/profile, snapshots и журнал; передать факты
   read-only штатному verifier в чистом отдельном sandbox с приватными tests.
   Verifier читает артефакт как данные и никогда не исполняет его.
8. Запустить предметную проверку T1: эффект, адресат/текст/кратность и сохранность.
   Разделить process status, заявление workflow и результат критериев с refs.
   Пока методики нет, score отсутствует; техническое выполнение не называется
   полноценным оцениваемым запуском. Сохранить минимальный результат со ссылками
   на штатные Harbor logs, а не второе дерево логов. Выполнить адресный cleanup.

Проверку штатного порядка фаз сделать на этом минимальном пути до расширения
симулятора. Если стандартные операции не позволяют забрать артефакт, выполнить
отдельный replay и доставить trusted bundle до `tests/test.sh`, сохранить
минимальный воспроизводитель с версиями и точным недоступным действием.
Только после этого проверить **один** host-side BaseVerifier hook, связывающий
те же фазы. Не создавать одновременно обе реализации. Решение о hook и причина
должны быть доступны WB-05; одного существования extension seam недостаточно.

## Что явно не входит

Полный Telegram, UI, T2–T4, MCP для Composer без текущей необходимости,
интеграции Codex/Sapiens, Judge, полный repair loop, численная методика,
модельные вызовы, собственный orchestrator, второй runtime или язык workflow.
Не запускать Harbor/n8n из `tests/test.sh`, не монтировать туда Docker socket.

## Затрагиваемые компоненты

Минимальный `tasks/t1-send-message`, нужная часть `simapps/telegram`, общие
execution/contracts, связь штатных операций Harbor, минимальная Evaluation
и используемые environments. Telegram-правила находятся в Task/предметном
модуле. Общая обвязка не импортирует Telegram и не решает бизнес-задачу.

## Уместные проверки поведения

### Техническое уточнение первого прохода

Контракты и владение ресурсами — [ARCHITECTURE §3–6](../../ARCHITECTURE.md).
Точка сборки создаёт один E1Config с явными Task/output paths, digests образов,
конечными setup/execute/control/drain/verifier/total timeouts, CPU/RAM/max_calls.
Нативные Harbor timeout overrides производятся из него, без независимых defaults.
`run_manual` создаёт один Attempt; каждый replay получает новый ID, новую БД,
свой state и capability. `replay` заимствует Harbor environment; harbor.py владеет
созданием/stop/cleanup, Task script владеет бизнес-проверкой, не lifecycle.

Сначала проверить узкую передачу штатного lifecycle из ARCHITECTURE §4: collected file
после stop → отдельный replay → защищённые входы → separate verifier. Факт
наличия `TrialEvent.VERIFICATION_START` не закрывает доставку в verifier:
он ещё не создан, runtime mounts не наследуются. Записать доступное публичное
действие передачи либо точное ограничение. Лишь затем при доказанной необходимости
проверить один BaseVerifier hook; приватные методы Trial не становятся нашим API.

Технический профиль T1 API согласован владельцем до предметных контролей:
`get_chat(chat_id)`, `list_messages(chat_id)`, `send_message(chat_id, text)`;
вход/выход JSON, точный ID, `not_found` без эффекта. Отправка без idempotency key:
каждый принятый write создаёт новое сообщение. Публичное чтение сообщений даёт
ID/адресата/текст для наблюдения эффекта; выборки полные только в объявленном
конечном пределе, превышение — явная ошибка. История отправки не подставляется
в BenchInput. Лимиты и tool wire-shapes фиксируются в одном app-owned tools
contract до контролей. Это технический профиль E1, не утверждённая методика WB-06.

После commit+потери ответа контроль либо наблюдает эффект разрешённым чтением,
либо сообщает unknown; слепой повтор запрещён. Серверный response=sent не означает,
что клиент получил ответ. В доверенных фактах acceptance/effect/response различны.
Fault injection доступна только host через тестовую конфигурацию simulator,
не как кандидатский tool и не через magic input в рабочем запросе.

WB-04 фиксирует shape Set/BenchInput, единственного BenchResult и allowlist
typeVersion/options на выбранных n8n images; artifact profile не расширяется.
Извлечение claim и execution ID проверяется настоящим CLI; без корректного
выхода claim отсутствует, бизнес-факты всё равно получаются от simulator.
Результаты без scoring/success policy имеют score=null, общий verdict=unknown
и явные статусы критериев; успешность инженерного контроля оценивается по таблице
ниже, а не фиктивным Harbor reward.

| Interface | Поведение / что обнаруживает | Чего не доказывает | Настоящий запуск или подмена |
|---|---|---|---|

| S4: `run_manual` / `replay` через Harbor | Один контроль на новых inputs; отдельный n8n+JS runner, свежий мир, stop и передача фактов до verifier | Поздние Composer/UI/Judge, надёжность на непроверенных версиях | Реальный Docker/Harbor/n8n, opt-in integration |

После согласования сначала один локальный отказ артефакта → минимальный приём;
затем техническая lifecycle-проба → реальный положительный T1 → новый input.
Предметный отрицательный пример проверяется независимо от сданного контроля.
Каждый следующий сценарий начинается со своего наблюдаемого сбоя; заранее
вся матрица тестовыми файлами не материализуется. Все прежние контроли и критерии
готовности ниже сохраняют силу.

| Контроль | Наблюдаемое доказательство |
|---|---|
| Новый chat_id и текст, один исходный workflow | Реальный эффект n8n, правильные адресат/текст, ровно одно новое сообщение и сохранность старых данных; исходный hash одинаков |
| Отсутствующий чат; одинаковые display names при разных ID | Явный отказ без записи в первом случае; точная адресация по input ID во втором |
| Сдача отдельно от исполнения | До replay действий нет; файл контроля проходит тот же validator/runtime/verifier, не выдаёт себе reward |
| Свежесть | Другой кейс получает своё исходное состояние и новую БД; предыдущие отправки и static data не улучшают результат |
| Настоящий Code node | Логи подтверждают выполнение JS через совместимый external runner внутри реального n8n CLI-контроля |
| Базовая граница доверия | До размещения checks подтверждены separate verifier и отсутствие tests/solution/checkout/socket/control-secret в candidate/replay/runner; контрольный маркер приватных данных не читается из этих сред |
| Недостаточность штатного пути | При наличии ограничения — конкретный failing reproducer и результат единственного минимального hook; при отсутствии — только штатный путь |

Быстрые проверки validator/binder проверяют запрет credentials, pinData/static
state, лишних triggers/integrations, неправильных slots и сохранение логики.
Они дополняют интеграцию; обходные network/file попытки и сбои закрывает WB-05.

## Критерии готовности

Реально выполнены положительные контроли таблицы через Harbor и n8n/runner;
получен отдельный независимый результат по frozen facts. Приватные checks
не соседствуют с недоверенным исполнением. Записаны версии, bindings, hashes,
команды, технические лимиты и расположение evidence вне Git. README содержит
проверенную команду технического контроля отдельно от быстрых проверок.
Ограничения и непроверенные сценарии явно переданы WB-05. Никаких заявлений
об успешном E1 целиком, полном score или совместимости Composer.

## Что останавливает работу и требует решения

Нет Docker/совместимых images, external runner не работает с CLI, сеть/файлы
не изолируются на выбранном host, штатный путь и минимальный hook не обеспечивают
передачу фактов. Потребность копировать Trial, создавать собственный orchestrator,
исполнять кандидат рядом с tests или расширять продуктовые контракты — stop.
Сохранить команды/ошибку и точный вопрос владельцу; mock не заменяет успех.

## Передать следующей задаче

WB-05 получает воспроизводимую команду, ручной native-контроль, реальные версии,
путь и схему доверенных фактов, результат проверки lifecycle, правила T1 API,
точки управляемых fault-инъекций и список ещё недоказанных отрицательных контролей.


## Выполнено в WB-04

Native T1 проходит штатный oracle → collection после stop → приём/validation →
единственный n8n CLI import/execute → revoke/freeze/stop → защищённые native tests →
штатный separate verifier. Lifecycle-проба подтвердила передачу через публичный
VERIFICATION_START до upload tests; BaseVerifier hook не потребовался. Core не
импортирует Telegram, не изменяет бизнес-логику и не запускает модели.

Согласованный профиль реализован в app-owned tools contract: точный ID,
not_found без записи, полный T1 list до 100 сообщений, выше limit_exceeded;
каждая принятая отправка создаёт новое сообщение, idempotency key и автоматических
повторов отправки нет. Verifier проверяет snapshots и журнал, получателя,
точный текст, кратность и сохранность. Предел 100 не применяется к state целиком
и не объявляется лимитом будущих T3/T4.
