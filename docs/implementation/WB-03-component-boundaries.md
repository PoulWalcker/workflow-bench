# WB-03 — организация компонентов и границ данных

Статус: **DONE** (11 октября 2026 года). Этап 1 [ROADMAP](../../ROADMAP.md). Это отдельная актуальная
задача; исторический `01-project-structure.md` / WB-01 не переиспользуется.

## Цель и наблюдаемый результат

Минимальный пакет принимает путь native Task и готовит публичный пакет на малом
синтетическом примере. Приватные данные остаются на доверенной стороне. Есть
реальный первый участок Definition → Experiment, на который E1 сможет опереться,
без создания пустых будущих подсистем.

## Основание

- [SPEC §3, §6, §10–11](../../SPEC.md): Task-first, разные назначения данных,
  публичная сдача и изоляция.
- [ARCHITECTURE §1](../../ARCHITECTURE.md): владельцы и направления импортов;
  §2 «Task materials and data boundaries», §4 «Harbor lifecycle and trust topology»: native Task,
  public export, расположение общих и предметных частей.
- [Engineering rules](../../AGENTS.md): реальные обязанности, один владелец,
  конфигурация и проверки поведения.

## Зависимости

[WB-02](WB-02-bootstrap.md) завершён, команды среды проверены. Тикет не требует
Docker, моделей или утверждения численной рубрики T1.

## Что входит

1. Закрепить размещение реально появляющегося кода по принятой архитектуре:
   общие обменные структуры и загрузка данных — без Telegram-семантики;
   точка сборки принимает Task path. Схемы проверяются на внешней границе.
2. Реализовать минимальное чтение native config и публичных данных Task,
   достаточное для подготовки public export. Использовать native Harbor config,
   не создавать альтернативный Task framework. Точную разбивку кода выбрать
   по появившимся обязанностям, не по количеству файлов диаграммы.
3. На малой тестовой fixture различить input schema/публичный example, приватные
   cases.state/expected, tests и solution. Публичный `example.state` разрешён;
   приватный state не должен утекать по сходству структуры. Собирать явный набор
   разрешённых материалов, не копировать checkout целиком.
4. Подготовить ровно нужную E1 часть общего контракта артефакта/public package.
   Готовить конечный public export как вход отдельного sandbox/build context.
   Профиль tools передаётся окружением, а не зашивается бизнес-ветками в core.
5. Зафиксировать правила расширения в локальной документации реализованного
   интерфейса и проверенных командах README; архитектуру заново не проектировать.
   Exchange-схемы не импортируют app или конкретный Composer.

## Что явно не входит

Работающий Telegram, n8n, lifecycle Harbor, verifier, score, repair loop,
Sapiens package и Judge. Не создавать их пустые классы/каталоги, registry,
универсальные backends или функции с `NotImplementedError` ради структуры.
Загрузка синтетической Task не считается настоящей Harbor-интеграцией.

## Затрагиваемые компоненты

Минимальная Definition/общие contracts, вход сборки и тестовые fixtures.
Будущие Telegram и Sapiens остаются за пределами core, но появляются только
когда соответствующая задача реализует поведение. Execution и Evaluation здесь
имеют определённые архитектурой обязанности, а не обязательные пустые файлы.

## Уместные проверки поведения

### Техническое уточнение и test seam S2 (согласован пользователем)

Реализовать только `definition.py` и реально необходимые exchange-структуры
из [ARCHITECTURE §2](../../ARCHITECTURE.md): `load_task` →
`export_public`. Зависимости здесь — native Harbor parser и jsonschema;
установка Harbor не запускает его lifecycle и не подтверждает E1.
`TaskMaterials` не является новым Task framework. `tool_contract` передаётся
явно из синтетической fixture; получать его из app image предстоит WB-04.

Публичный экспорт имеет законченный каталог и список hashes, ошибки — код и
безопасную относительную ссылку. Caller владеет конечным каталогом, exporter —
своим временным каталогом до атомарного завершения. Пути схем читаются из
ресурсов установленного пакета; `cwd` не участвует в поиске контрактов.
Native nodes/typeVersion, runtime/control и evaluation schemas здесь не
реализуются наперёд; общий workflow contract не выдаёт их совместимость за факт.

| Interface | Поведение / что обнаруживает | Чего не доказывает | Настоящий запуск или подмена |
|---|---|---|---|
| `load_task` → `export_public` | Явный публичный набор, сохранение учебного state; приватные маркеры исключены; неверная schema, traversal, symlink и конфликт destination дают отказ; вторая Task проходит без регистрации | Контейнерную изоляцию, реальный Harbor Trial, E4 | Настоящие временные файлы, native parser и JSON validator; без подмены наших модулей |

TDD после согласования: минимальный разрешённый export → один приватный marker →
unsafe path → повреждённый JSON → другая Task. Каждый сценарий — отдельный
red → green; конкретный следующий тест выбирается по обнаруженному поведению,
не создаётся сразу вся suite. Проверка содержания export допустима: это его
Interface, а не тест внутреннего дерева исходников.

- Экспорт включает постановку, схемы, разрешённые описания tools и учебный example,
  но исключает маркеры из cases, tests, solution, служебных документов и secrets.
- Невалидные внешние данные и ссылки, выходящие за разрешённые материалы Task,
  дают понятную ошибку; symlink/path traversal не расширяют экспорт.
- Рабочие input, состояние для Simulator и expected для verifier остаются
  разными назначениями данных; полная приватная fixture не становится input.
- Другая синтетическая Task той же формы загружается по пути без регистрации
  и ветвления по имени. Это тест загрузчика, не доказательство E4.
- Проверить реальные импорты на отсутствие зависимости core от Telegram/Composer;
  не писать тесты на точное дерево пустых файлов.

## Критерии готовности

Минимальная загрузка/public export работают и имеют поведенческие проверки.
Есть один источник общего контракта и понятный путь передачи результата в E1.
Каждый новый модуль выполняет текущую обязанность. Быстрые тесты и Ruff проходят;
содержимое экспорта проверено. Sandbox-изоляция ещё не объявляется доказанной.

## Что останавливает работу и требует решения

Native config требует сменить выбранную границу Task; публичные и приватные
данные невозможно разделить без изменения контракта; появляется необходимость
нового registry/DSL или доступа кандидата к checkout. Зафиксировать конкретный
вход и конфликтующий пункт документа, не обходить его новой абстракцией.

контракты. Native Harbor 0.24.0/config parser и jsonschema 4.26.0 проверены на
настоящих временных файлах, без lifecycle. Подтверждён только S2: 76 fast-проверок,
включая отрицательные контроли и независимую вторую Task. Общая suite — 99 passed;
Ruff lint/format и `git diff --check` проходят. Wheel export из другого cwd

и ограничения восстановления среды принадлежат [README](../../README.md).
Все критерии этого тикета выполнены. WB-04 получает этот публичный пакет;
runtime, schemas исполнения/evaluation, приватные case loaders и настоящая
изоляция остаются его последующей работой. WB-04 здесь не начат.

Локальный code-quality review исправил дублирование контрактных имён и ошибки
S2 (совпадение private path с instruction, native parser recursion и неразрешимые
refs). Внешний Interface и набор public package сохранены; новые отрицательные
контроли прошли red → green. Перенос gate в `tests/conftest.py` подтверждён всеми
23 согласованными сценариями S1, содержимое hooks сохранено побайтно.

## Historical packaging and export verification

Moved from the former README; the results below refer to the original WB-03 runs.

Проверенная команда S2 (обычные временные файлы, настоящий native parser и validator):

```sh

```

при сбое записи. Последний контроль подменяет только файловую запись для ошибки
ОС; loader/exporter не подменяются. Вторая синтетическая Task проходит по пути
из другого cwd без регистрации. Импорты core просмотрены: предметных зависимостей
от Telegram/Sapiens нет. S2 не доказывает настоящий Harbor Trial или исполнение n8n.

### Packaging

В WB-03 выполнена изолированная PEP 517 сборка:

```sh
uv build --force-pep517 --offline
```

Wheel и sdist содержат пакет с ресурсами; кэши, среды, tests, служебные документы
и личные файлы исключены. Из собранного wheel установлен пакет в отдельный временный
`--target` через `uv pip install --offline --no-deps`; Python `-I` из другого cwd
импортировал именно этот установленный пакет и выполнил native load/public export
на синтетической fixture. Dependencies брались из проверенной locked `.venv`.
Это проверка поставки ресурсов wheel, не восстановление зависимостей с чистого кэша.

Первый `uv build --force-pep517` без offline не прошёл из-за DNS в sandbox;
повтор с offline использовал кэш и завершился exit 0. Попытка восстановить отдельную
wheel-среду только из кэша через `uv pip install --offline` также не прошла:
resolver не нашёл registry distributions части зависимостей. Для чистой установки
по-прежнему нужна сеть. Default fast pytest сети не требует.
