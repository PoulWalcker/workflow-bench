# Workflow Bench — независимый продуктовый челендж

11 октября 2026 года. Основа: приложенный `workflow-bench-challenge-brief (2).md`, версия 1.0, далее **brief**. Это review постановки, а не новая спецификация и не отчёт о работающем стенде. Исходный brief, SPEC, ARCHITECTURE и ROADMAP не изменены.

## 1. Общий вывод

**Постановка условно готова к архитектурному планированию границ, но ещё не к фиксации подробной архитектуры и сравнительному эксперименту.** Проблема сформулирована достаточно ясно: проверять создание переносимой между входами автоматизации, сократив стоимость сопровождения исследовательского стенда. Четыре задачи дают полезную лестницу сложности. Перезапуск оправдан целью упростить работу, но сам по себе её не достигает: новый язык графа, собственный bridge и универсальная интеграция Task способны воспроизвести старую сложность.

До детализации нужно определить границу T3 и амбицию вывода об эффективности; затем проверить один сквозной технический срез. Рекомендуемый первый релиз сохраняет **все T1–T4, виртуальный UI, exploration, исправления, независимую проверку и численный score**. Начать с T1 разумно; объявить T1 готовым MVP — подмена согласованного scope.

### Что именно измеряется

Единица наблюдения — **зафиксированный workflow на новом кейсе**, полученный конкретной связкой model + Composer/harness + tools + бюджет. Единица сравнения — весь процесс получения и исполнения выбранной версии при одинаковых условиях. Compiler и заранее написанные инструменты входят в измерительный стенд: если они уже решают бизнес-задачу, вклад AI перестаёт быть различимым.

| Гипотеза | Что позволяют T1–T4 | Чего они не доказывают; минимальная поправка |
|---|---|---|
| H1: повторное использование | T1 меняет параметры; T3 — ветви; T4 — состав и число объектов. Один артефакт должен работать без правки логики | Успех на известных примерах не означает обобщение. Итоговые кейсы должны менять не только текст/ID, но и релевантную структуру: пустое множество, несколько совпадений, неоднозначность |
| H2: UI без runtime LLM-навигации | T2 проверяет поиск в текущем дереве и действие после исследования | Перестановка узлов проверяет ограниченную устойчивость, не произвольный редизайн и не настоящий Telegram. Публично обозначить класс допустимых изменений; старый числовой path должен иметь отрицательный контроль |
| H3: выбор эффективных tools | T1/T2 дают парное сравнение отправки; T3/T4 показывают выбор при API+UI | Свободный выбор не доказывает оптимальность или комбинирование. Сравнивать одну задачу на одинаковых кейсах при разных профилях. Если API решает всё, выбор только API допустим |
| H4: польза исправлений | Видны результаты первой и выбранной версий, потраченные попытки и ресурсы | Рост на feedback-кейсах может быть подгонкой. Для вывода о переносе исправлений сравнить первую и выбранную версии на итоговых кейсах только после завершения выбора; эти результаты не возвращать Composer |

T1 прежде всего проверяет исправность стенда, а не сложное планирование. T3 с шаблонами проверяет условия и применение правил, а не свободное смысловое рассуждение. T4 проверяет обработку коллекций и идентичность объектов, но не конкурентные транзакции. Общая симуляция полезна для сопоставимости, однако четыре Telegram-задачи не представляют все бизнес-процессы.

Нельзя приписывать разницу Codex/Sapiens исключительно модели, считать наличие exploration доказательством его пользы или делать вывод о надёжности по одному успешному созданию. Для причинного вывода о пользе exploration потребовалось бы отдельное сравнение с тем же Composer без него; **для первого MVP оно не обязательно**. Малый фиксированный набор даёт результаты на этих кейсах, не оценку частоты успеха во всём мире.

**Экономия пока не измеряется относительно альтернативы.** Нужны затраты создания и исправлений A, исполнения одного входа R и разового агента D на сопоставимом качестве. Лишь при D > R возможна окупаемость примерно после N > A / (D − R) использований. Это условная модель, не установленный результат. Время, токены и деньги не смешивать без явного способа пересчёта; Judge и инфраструктуру показывать отдельно. Рекомендация: в первом релизе измерять затраты, а обещание экономии отложить до небольшого парного baseline. Это ограничение вывода, не исключение эффективности из отчёта.

Есть и вторая цель — уменьшить сложность сопровождения. Её не измеряет score кандидата. Практический критерий: добавление следующей задачи в поддержанном контракте не требует знания внутренних деталей runner и правок core; неизвестный результат запуска можно объяснить по одному отчёту. Число файлов или соответствие rTernarity не заменяет этот критерий.

### Происхождение утверждений и проверка источников

**Требования пользователя:** повторно используемый workflow, четыре задачи, API/UI/совместный доступ, exploration, ограниченные исправления, свежие состояния, score, независимый core и заменяемый Composer — brief §3. Работа прежнего benchmarking — прямое сообщение пользователя; в этом review она не воспроизводилась.

**Рабочие предложения, допускающие челендж:** typed graph → n8n, Harbor/Docker, конкретный adapter, первая успешная/последняя версия, численная рубрика и граница включения Sapiens — brief §§3, 5, 6, 8, 10. Наличие этих решений в локальных проектных документах не превращает их в дополнительно подтверждённые пожелания пользователя. Все рекомендации ниже — предложения данного review.

## 2. Пять главных рисков

| Приоритет и основание | Реальный риск и последствие | Самое маленькое исправление |
|---|---|---|
| **1. Вывод шире измерения** — brief §§1, 7–8 | Успешный replay объявят общей надёжностью или экономией; различие harness — различием моделей. Инфраструктура растёт ради эффекта, который эксперимент не может показать | Зафиксировать единицу сравнения, класс изменений и границы выводов из §1. Не обещать экономию без парного baseline и полной стоимости создания |
| **2. Язык выбран до проверки выразительности; T3 не определена** — brief §§3, 7–8, R2 | Для UI-поиска и T4 потребуется либо семантика обработки коллекций, либо бизнес-логика в tools/compiler. Свободный ответ T3 может незаметно добавить runtime model calls | Для T3 рекомендованы публичные правила/шаблоны. До заморозки graph проверить на ручном артефакте поиск, ветвления и переменное число действий; сохранять typed graph только при доказанной пользе ограничения |
| **3. Изоляция и наблюдаемый результат ещё не обеспечены** — brief §5, R4, R8, R10 | Candidate может обойти UI-only, читать tests или подделывать evidence; повтор после потерянного ответа создаст дубль. Название Docker/Harbor этого не исправляет | Доверенные факты со стороны среды, фактическое ограничение доступа, запрет слепого повтора неизвестной записи, отрицательные контроли. Candidate-код никогда не выполняется в доверенном verifier |
| **4. Правила измерения оставлены слишком поздно** — brief §§5, 8; SPEC §8; ROADMAP WB-04–06 | Без критерия успеха нельзя честно реализовать stop. Подбор весов после первых результатов, утечка через feedback и усреднение только оценённых кейсов искажают вывод | До первого оцениваемого запуска зафиксировать рубрику, выбор версии, разрешённый feedback и обработку неполноты. Технический smoke раньше допустим, но не является сравнением |
| **5. Заменяемость Composer смешивается с готовностью интеграции** — brief §6, R4, R7, R10 | Внешний bridge станет обязательным сервисом, а Sapiens — источником скрытого состояния и фоновой работы после timeout | Сначала штатный Harbor interface и один Codex adapter. Sapiens проверяет достаточность контракта; фактическое подключение — отдельный ограниченный эксперимент, без обещания заменить executable одной настройкой |

## 3. Проверка «что будет, если»

| Сценарий | Ожидаемое поведение | Достаточно ли требований | Где риск | Минимальное уточнение | Как проверить при реализации |
|---|---|---|---|---|---|
| **Новая Telegram-задача с существующими tools** | Новые постановка, данные и verifier; общий симулятор используется повторно; core, общий prompt, compiler и scoring-алгоритм неизменны | Направление задано в §4.3; граница поддержанного контракта пока не показана | «Независимость» обеспечат отдельной папкой, сохранив switch по task ID в runner; tool будет выполнять готовую задачу | Зафиксировать поддержанную семантику workflow/result и task-owned критерии. Пагинация обязательна только если включена в профиль | Неизменный граф на 0/1/N, повторах текста, уже пересланных и пограничном размере. Считать ожидаемые оригиналы и фактические пересылки, не только финальный ответ workflow |
| **Меняется расположение UI** | Детерминированное повторное чтение дерева и поиск сохраняют выполнение в согласованном классе изменений | Частично: динамический tree согласован, инварианты нет | Постоянные скрытые IDs или готовый `sendToRecipient` делают UI-задачу фиктивной; произвольный редизайн делает её неразрешимой | Сохранить публичные семантические признаки, менять позиции/обёртки в заявленных пределах. При неподдержанной неоднозначности — безопасный отказ; при новом интерфейсе исправление только между попытками | Переставить узлы, изменить текущий экран и черновик. Старый path ведёт к неверному элементу/ошибке, поиск на свежем дереве проходит. Проверка адресата обязательна |
| **Действие выполнено, ответ потерян** | Workflow не дублирует запись; verifier устанавливает факт по защищённому состоянию, отдельно фиксирует незнание кандидата | Честная неизвестность предусмотрена, механизм восстановления не задан | Любой timeout трактуется как «не сделано»; проверка совпадающего текста путает старое и новое сообщение | Повтор допустим при гарантированной idempotency операции либо однозначном read-back. UI не получает волшебную идемпотентность. Если разрешённые наблюдения не различают исходы, остановиться с неопределённостью; это допустимая обработка сбоя, но не автоматический полный успех | Два случая: обрыв до commit и после commit; старое одинаковое сообщение как помеха. Проверить отсутствие дубля, состояние, декларацию результата и отсутствие скрытого retry runner |
| **LLM Judge недоступен** | Известные программные результаты сохраняются. Если Judge обязателен — оценка неполная; без смысловых критериев запуск оценивается полностью | Почти да, §8 и SPEC §8; stop при неполноте требует уточнения | Missing превращается в 0 или исключается из среднего; ради Judge повторно выполняется workflow | Полный score = `null`, полнота отдельно; известный критический провал сохраняется. При обязательном Judge приостановить оценивание, не посылать Composer выдуманный feedback; оценивать повторно уже записанные факты без replay действий | Отключить Judge, вернуть повреждённый ответ/несуществующую evidence-ссылку. Нет ложного success, полного среднего или повторной отправки сообщения |
| **Workflow обходит tools или подменяет проверку** | Обход не даёт запрещённого доступа или успешного reward; содержимое чатов и candidate-файлы не становятся инструкциями verifier | Требование ясное; реализация неизвестна | Доступ к admin/reset/state, чужому run, сети, файлам tests; поддельные logs/reward; prompt injection в Judge | Право на действие проверяется средой. Проверяющий читает факты доверенного происхождения, привязанные к run/case/версии; кандидат не может заменить их своим экспортом. При попытке обхода — явный провал policy, а не успех за красивый отчёт | Отдельные отрицательные контроли на UI-only→API, чтение приватного маркера, запись поддельного reward, подмену журнала и инструкции Judge в сообщении. Проверить фактический отказ и отсутствие утечки; ссылки Judge на существующие события сами по себе не доказывают смысловую устойчивость |

Сброс между кейсами не противоречит проверке дублей: уже пересланные сообщения входят в исходное состояние конкретного кейса, а повторный вызов/потеря ответа моделируется внутри него. Это не требует долгоживущего межкейсового ledger.

## 4. Предлагаемые изменения: сохранить / изменить / отложить

| Решение | Что именно и почему | Последствие / цена |
|---|---|---|
| **Сохранить** | Все четыре задачи, одну общую симуляцию, три профиля доступа, exploration, свежие состояния и исправления. Они проверяют разные необходимые свойства | MVP больше API-demo, но не требует второго приложения или настоящего desktop |
| **Сохранить** | Кодовые проверки, score 0–10 и отдельный вердикт; Judge только для содержательного критерия, который нельзя надёжно проверить правилом | Judge может не понадобиться T1/T2/T4 и шаблонной T3. Не добавлять субъективную «красоту текста» ради демонстрации Judge |
| **Сохранить условно** | Harbor и один n8n runtime; небольшой typed graph как проверяемое ограничение допустимых операций | Сначала подтвердить, что ограничения упрощают проверку и покрывают T2/T4. Если граф лишь оборачивает произвольный JavaScript и n8n expressions, честно сравнить его с ограниченным native n8n-артефактом; не поддерживать оба формата и не писать универсальный DSL |
| **Изменить: уточнить T3** | Публичные правила и шаблоны, без runtime LLM-генерации в первом релизе | Проверяются условия, соответствие правилам и выбор tools; вывод о свободной генерации ответа откладывается. Это рекомендация по открытому вопросу brief, не уже принятое решение |
| **Изменить: рубрика до измерения** | Оценивать бизнес-результаты, а не число пройденных мелких assert. Рекомендованы равные веса независимых обязательных результатов как старт, критический провал всегда даёт fail; качество — только по явной рубрике. Эффективность сначала показывать отдельными метриками | Score не покупает успех ценой неверного адресата. Бонусы за скорость/число tools не вводятся до обоснованного нормирования. Численные веса и правила частичного результата утверждаются до оцениваемого запуска |
| **Изменить: агрегация и stop** | Рекомендуется среднее score всех заранее назначенных кейсов при полной оценке плюс число успешных/всех и критические провалы. Успех версии — выполнены все обязательные условия набора для исправлений. Сохранить выбор первой успешной, иначе последнего результата | Один fail не скрывается средним; missing делает полный итог отсутствующим. Последняя невалидная версия остаётся видимой. Общий рейтинг четырёх разнородных задач пока не нужен |
| **Уточнить границу hybrid** | Совместная доступность API+UI остаётся обязательной. Проверка обязательного комбинирования, если нужна, требует взаимодополняющих возможностей: ни один интерфейс по отдельности не решает кейс | В SPEC §12 предлагается «хотя бы один ограниченный API-case», но этого недостаточно: всё может решаться через UI. Brief §7 уже корректно различает эти случаи. Не превращать forced hybrid в доказательство свободного выбора или в пятую задачу |
| **Изменить: граница feedback и бюджет** | Публичные требования, ограниченный feedback о development-проверках, итоговые кейсы без исправлений. Кроме `max_attempts`, конечные лимиты времени и tool/model-расхода; переносимый контекст и повторные обращения учитываются | Больше tool calls внутри одного CLI-запуска не дают бесплатную попытку. Неизвестный модельный исход не повторяется автоматически; не требуется отдельная система учёта платежей |
| **Отложить** | Реальную Sapiens-интеграцию до доказанного Codex-пути, но сейчас проверить её требования к общей границе Composer | Первый релиз не доказывает заменяемость реальным вторым Composer; он не должен этого обещать. Требование заменяемости сохраняется |
| **Отложить** | Сравнение экономии с разовым агентом, свободную runtime-генерацию, произвольные UI-редизайны, склад как продуктовую задачу | Сужается сила выводов, не согласованный набор Telegram-задач. Возврат к этим экспериментам потребует отдельной цели и конечного бюджета |
| **Не вводить** | Обязательный HTTP bridge, registry плагинов, scheduler, универсальный backend, отдельную Static App Model, dashboard, миграцию старого evidence | Сохраняется небольшой исследовательский инструмент. Код нового окружения и verifier допустим без новой платформы |

## 5. Открытые вопросы и рекомендуемые решения

### Что решить пользователю

| Вопрос | Рекомендуемый вариант | Почему меняет следующий шаг |
|---|---|---|
| Нужна ли в T3 свободная генерация ответа при исполнении? | В первом релизе правила/шаблоны; runtime LLM не вызывать | Иначе появляются ещё один источник недетерминизма, отдельные затраты, права на модельный вызов и другая выразительность workflow |
| Обязателен ли для первого релиза вывод об экономии относительно разового агента? | Нет: повторное использование и прозрачные затраты сейчас; сравнительная экономия отдельным экспериментом | Если обязателен, небольшой сопоставимый baseline становится частью релиза, а не факультативным последующим анализом |

### Что передать архитектору

| Недостающее решение | Рекомендация и проверяемая граница |
|---|---|
| Достаточность graph | Выбрать минимальную поддержанную семантику для свежего UI-поиска, ветвлений и коллекций, без task-specific узлов. Не замораживать только по успеху T1; произвольный JS не считать автоматически безопасным |
| Composer lifecycle | Общий результат: артефакт или явный неуспех/неизвестность, завершение/остановка, идентичность harness и наблюдаемые затраты. Контекст чист между независимыми экспериментами; между исправлениями передаётся только разрешённое знание |
| Граница Task/core | Окружение владеет предметными действиями, Task — критериями; core обрабатывает их результаты. Новые schemas/tools допустимы в прежней семантике, новые виды исполнения требуют явного расширения |
| Профиль UI и идентичность | Описать наблюдаемые признаки, поиск, допустимые изменения дерева и пределы данных. Не раскрывать весь state через tree; не вводить скрытые готовые селекторы решения |
| Неопределённость, score и stop | Разделить факт эффекта, статус исполнения и полноту оценки. Рекомендуемое поведение — в таблице сценариев; не сводить всё к одному success/exit code или числу reward |
| Рубрика и feedback | Зафиксировать предложенные правила агрегации, критические условия и поля feedback до измерений; владелец конкретных весов и ожиданий — Task. Текст скрытого кейса не передавать в диагностическом dump |

### Что проверить техническим экспериментом

| Предположение | Рекомендуемая проверка | Что пока неизвестно |
|---|---|---|
| Harbor+n8n подходят без собственной платформы | Реальное исполнение фиксированного графа, отдельная проверка, защищённые факты, конечная остановка и точечный cleanup | Совместимость закреплённых версий, реальное размещение фаз, изоляция и сохранность результатов |
| Штатный Codex adapter достаточен | Контролируемое exploration через разрешённый tool, сдача graph, ошибка tool и timeout; проверка отсутствия приватного контекста | Auth, ограничения инструментов и сети, полный lifecycle. Модельный запуск только после отдельного разрешения с конечным бюджетом |
| Sapiens удовлетворяет той же границе | Изолированный CORPORA-контекст, только симулированные tools, выдача графа, disconnect/cancel и проверка отсутствия поздних действий | Возможность такого режима на выбранном host/backend; документация CLI этого не гарантирует |
| Judge пригоден там, где действительно нужен | Малый вручную размеченный набор, включая неверные утверждения и инструкции оценщику внутри данных; неизменная рубрика | Стабильность и устойчивость смысловой оценки. Валидный JSON и существующие evidence refs не равны правильному суждению |

**Один первый проверяемый шаг:** небольшой стенд без модели по смыслу P2 brief, с проверкой выразительности, а не только «hello world». Вход — ручной неизменный граф, публичный профиль tools, несколько фиксированных кейсов с переставленным деревом и 0/1/несколькими объектами. Наблюдаемый результат — настоящий n8n совершает правильное число разрешённых действий, а отдельный verifier оценивает защищённые факты; новая маленькая Task с прежними контрактами не требует бизнес-правок core. Это технический контроль, не пятая задача MVP и не доказательство способности Composer.

Отрицательные контроли того же среза: фиксированный UI-path, неверный адресат/дубль, поддельное свидетельство успеха, попытка прочитать приватный маркер, бесконечное выполнение и потерянный ответ после записи. **Не расширять систему**, если проверка доверяет данным кандидата, кандидат достигает tests/admin, для обхода коллекции требуется бизнес-патч compiler или остановленный run продолжает действия. Если стенд проходит, это разрешает проверять Composer; низкий результат модели сам по себе не означает дефект стенда и не оправдывает ослабление проверок.

### Что действительно сделано в этом review

Прочитаны brief, AGENTS, Principles, относящиеся разделы ROADMAP/SPEC/ARCHITECTURE; проверены указанные выше первоисточники через web, GitHub и `curl`. Использовались `git status --short`, `test`, `cat`, `sed`, `rg` для чтения и проверки документа. `git diff --check` завершился с кодом 0; отдельная проверка нового неотслеживаемого файла `git diff --no-index --check /dev/null PRODUCT_REVIEW.md` не сообщила ошибок пробелов (код 1 означает наличие различий). Проверка структуры подтвердила пять требуемых разделов и два финальных вопроса. Часть web-запросов к raw GitHub вернула cache miss; отдельный shell-запрос — DNS-ошибку; нужные файлы получены последующими успешными чтениями. Код внешних репозиториев не исполнялся и не переносился.

Docker, Harbor trials, n8n, Codex Composer, Sapiens и Judge **не запускались**; модельные вызовы для benchmark не делались. Тесты приложения и линтинг кода не запускались: изменён только этот документ. Анализ исходников не является доказательством работающей изоляции или интеграции.

### Два блокирующих продуктовых вопроса

1. **Фиксируем T3 первого релиза как ответ по публичным правилам/шаблонам без runtime LLM-генерации?** Рекомендация — да; свободную генерацию вынести в отдельный эксперимент.
2. **Достаточно для первого релиза доказать повторное использование и показать затраты, без обязательного вывода об экономии относительно разового агента?** Рекомендация — да; если нет, в релиз нужен небольшой парный baseline.
